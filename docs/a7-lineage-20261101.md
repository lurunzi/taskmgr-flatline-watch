# A7: live address-chain trace from an exhausted query to the identity conflict, 1 November 2026

**English** · [中文](#zh)

English is the controlling text.

## Result

**One live Task Manager instance was traced from an exhausted query, through conversion and cache moves, to the identity-conflict branch that produces `0x8007139F`. The same instance then froze.**

- The address link is closed: the conflicting entity is the object recorded as descending from the exhausted query's PID 0 / CreateTime 0 record. The independent audit confirmed the ancestry and the query shape.
- The audit's strictest criterion is still open: the aggregation-vector entry at the conflict was not recorded.
- The `0x8007139F` report itself was not recorded in this run.

## Setup

- Owner-authorised A7 run with `tools/capture-address-chain.py --pid 71396 --minutes 40 --process-events`.
- The tool ran elevated with cdb breakpoints at the pinned 9549 sites; all 15 byte signatures were verified, including the conflict branch at RVA `0x434D3`.
- The J17 thread-churn load ran at the same time (about 10,800 thread starts per second). Nothing was induced (`induced_queries: 0`).
- While the debugger was attached the watcher was stopped; it was restarted when the trace ended.
- The tool includes the fixes of commit `50f350f`.
- Evidence (read only):
  - trace: `D:\TaskmgrFreezeCaptures\a7-trace-20261101-230035\capture\`;
  - full dump taken at the conflict: `Taskmgr-origin.dmp`;
  - audit run on a copy: `a7-trace-20261101-230035-audit\`;
  - the freeze: `restart-20261101-231356-286417`.

## Chain (UTC, 1 November 2026)

| Time | Step | Identity carried |
|---|---|---|
| 23:11:43.657 | Q610 returns `S_OK` after three `0xC0000004` results and publishes 567 records; the tail record is at offset 1,642,360 | PID 0 / CreateTime 0 |
| 23:11:46.621 | `CONVERT` of that record into an entity | PID 0 / CreateTime 0 |
| 23:11:46–23:11:58 | `ASSIGN`, `COPY` and `MOVE` operations (address events 8–71) up to object generation 18 at `0x21dd1bcc8c0` | PID 0 / CreateTime 0 at every step |
| 23:11:59.927 | Breakpoint at `CreateAggregatorsForNewEntities` identity-conflict branch (RVA `0x434D3`, expected HRESULT `0x8007139F`), current object `0x21dd1bcc8c0` | current PID 0 / CreateTime 0 against existing PID 0 / CreateTime 134378462553662676 (the real Idle entry) |
| 23:13:24.305 / 23:13:56.283 | The watcher sees the same Taskmgr (PID 71396) as a flat candidate and confirms the freeze | — |

In the same 11 minutes the tool counted 392 normal queries, 217 third-call successes (each rejected as `E_OUTOFMEMORY`) and 1 exhausted query with a ghost tail.

## What is and is not shown

- **Shown:** the PID 0 / CreateTime 0 record published by an exhausted query is the object that hits the identity-conflict branch. It collides with the genuine Idle entry, which also has PID 0 but a real creation time. This is the conflict proposed from the historical dumps, now observed in one live instance with continuous address tracking.
- **Not recorded in this run:**
  - the aggregation-vector entry at the conflict (`vector: null`). This is the only error in the independent audit (`missing aggregation vector entry`).
  - the `0x8007139F` report itself. The tool's ETL ends at about 23:12:12 and contains no such event; the trace also reports lost ETW events under the load, and failure reports may take a different path while a debugger is attached.
  - the tool's own post-detach freeze check. Its chart helper timed out; the freeze was confirmed by the watcher instead.
- **Timing:** the freeze was seen about 84 s after the conflict. During part of that time the process was paused for the dump and the debugger detach. The exact visible onset is not established because there was no connected normal sample.
- The first A7 run, `a7-trace-20261101-222205`, captured exhausted query Q262 and its moves but stopped on a tracker error (`KeyError(41)`), fixed in `50f350f`.

## Limits

- One instance, one machine, one DLL build (9549).
- Breakpoints change call timing. The run shows that the path exists, not how often it occurs naturally.
- Address equality and recorded operations establish identity of the object, not every internal step of `CreateAggregatorsForNewEntities`.

# A7：从耗尽查询到身份冲突的现场地址链追踪，2026 年 11 月 1 日

[English](#en) · **中文**

以英文为准。

## 结论

**在同一个正在运行的任务管理器实例里，从一次耗尽查询出发，经过数据转换和多次缓存搬运，一路追踪到了产生 `0x8007139F` 的身份冲突分支；随后该实例冻结。**

- 地址链已闭合：发生冲突的实体，正是被记录为源自耗尽查询那条 PID 0 / CreateTime 0 记录的对象。独立审计确认了祖先链和查询形态。
- 审计最严格的一项仍未满足：没有记录冲突时聚合数组中对应的条目。
- 本次也没有录到 `0x8007139F` 报告本身。

## 设置

- 负责人授权的 A7 运行，命令为 `tools/capture-address-chain.py --pid 71396 --minutes 40 --process-events`。
- 以管理员身份运行，cdb 断点设在已固定的 9549 位置；15 个字节签名全部核对通过，包括 RVA `0x434D3` 的冲突分支。
- 同时运行 J17 的线程增减负载（约每秒 10,800 次线程启动），没有人为诱发（`induced_queries: 0`）。
- 挂调试器期间监测器停止，追踪结束后重新启动。
- 工具已包含提交 `50f350f` 的修复。
- 证据（只读）：
  - 追踪数据：`D:\TaskmgrFreezeCaptures\a7-trace-20261101-230035\capture\`；
  - 冲突时的完整转储：`Taskmgr-origin.dmp`；
  - 在副本上运行的审计：`a7-trace-20261101-230035-audit\`；
  - 冻结事件：`restart-20261101-231356-286417`。

## 链路（UTC，2026 年 11 月 1 日）

| 时间 | 步骤 | 携带的身份 |
|---|---|---|
| 23:11:43.657 | Q610 三次返回 `0xC0000004` 后仍返回 `S_OK`，交出 567 条记录；尾记录位于偏移 1,642,360 | PID 0 / CreateTime 0 |
| 23:11:46.621 | `CONVERT`：该记录被转换为实体 | PID 0 / CreateTime 0 |
| 23:11:46–23:11:58 | 一系列 `ASSIGN`、`COPY`、`MOVE`（地址事件 8–71），直到第 18 代对象 `0x21dd1bcc8c0` | 每一步都是 PID 0 / CreateTime 0 |
| 23:11:59.927 | 命中 `CreateAggregatorsForNewEntities` 的身份冲突分支（RVA `0x434D3`，预期 HRESULT `0x8007139F`），当前对象 `0x21dd1bcc8c0` | 当前 PID 0 / CreateTime 0，对上已有的 PID 0 / CreateTime 134378462553662676（真实的空闲进程条目） |

同样这 11 分钟内，工具统计到 392 次正常查询、217 次第三次成功（每次都被当作 `E_OUTOFMEMORY` 拒绝）和 1 次带残缺尾记录的耗尽查询。

## 证实了什么，没证实什么

- **已证实：** 耗尽查询交出的 PID 0 / CreateTime 0 记录，正是命中身份冲突分支的那个对象。它和真实的空闲进程条目发生冲突：两者都是 PID 0，但后者带着真实的创建时间。这正是此前根据历史转储推断的冲突，现在在一个实例里通过连续的地址追踪直接观察到了。
- **本次未记录到：**
  - 冲突时聚合数组中对应的条目（`vector: null`）。这是独立审计唯一的报错（`missing aggregation vector entry`）。
  - `0x8007139F` 报告本身。工具自己的 ETL 截至约 23:12:12，其中没有该事件；该 trace 还报告了加压下的 ETW 事件丢失，而且挂调试器时，失败报告可能走另一条路径。
  - 工具自己在脱离调试器后的冻结确认。它的图表助手超时了，冻结改由监测器确认。
- **时间：** 冻结在冲突后约 84 秒被看到。这段时间里，进程有一部分时间因写转储和脱离调试器而处于暂停状态。由于没有衔接的正常样本，可见冻结的确切开始时间无法确定。
- 第一次 A7 运行（`a7-trace-20261101-222205`）捕获了耗尽查询 Q262 及其搬运过程，但因追踪器错误（`KeyError(41)`）中断，该问题已在 `50f350f` 修复。

## 局限

- 只有一个实例、一台机器、一个 DLL 版本（9549）。
- 断点会改变调用时序。本次只证明这条路径存在，不说明它在自然条件下发生的频率。
- 地址相等与记录到的操作只能确定对象的身份，并不覆盖 `CreateAggregatorsForNewEntities` 内部的每一步。
