# Task Manager CPU flatline: summary report

**English** · [中文](#zh)

English is the controlling text.

**Superseded at 23:45 UTC by the [full investigation report](investigation-report-20261101.md).** Since this page was written, the A7 trace has closed "query buffer → conflict" once under a debugger, and the N1 tally stands at 28 of 28.

State on 1 November 2026, 22:00 UTC. One page over the whole investigation; each line links to the document that holds the evidence. Live values are from `D:\TaskmgrFreezeCaptures\status.json` at that time.

## Conclusion

- **Cause located.** `ProcessDataGenerator::QueryProcessInformation` in `TaskManagerDataLayer.dll` has two retry defects: an exhausted query returns `S_OK` and publishes its buffer, and a successful third call is rejected as `E_OUTOFMEMORY`. Both are confirmed by controlled execution of the function's own machine code on 9278 and on the current 9549 file.
- **Freeze signature observed natively.** Every qualifying freeze carries the aggregation conflict `0x8007139F` (`aggregationdatamonitor.cpp:640 → :159 → Core.cpp:407`) about 9–29 s before the chart is seen flat; none has been recorded outside a freeze. Tally: 25 of 25 conforming.
- **Reproducible on demand.** Thread churn gave 9 freezes in one hour of load against 1 in one hour of quiet.
- **Not finished.** Only Microsoft can fix the DLL. Until then the watcher recovers each freeze automatically. The problem counts as resolved only after goals 1–3 of the [roadmap](roadmap.md) are met.

## What is established

| Finding | Evidence | Document |
|---|---|---|
| Two query retry defects in 9278 and 9549 | Controlled execution of the original function; 9549 negative control fails criteria 1 and 2, passes 3 | [investigation-status](investigation-status.md), [21 October review](flatline-incident-20261021.md) |
| The 9549 error at `ProcessDataSource2.cpp:821` sits in the caller of `QueryProcessInformation` | Public symbols (J8) | [roadmap](roadmap.md) |
| `0x8007139F` marks each freeze | 25 of 25 qualifying freezes; 0 outside freezes | [cross-incident table](cross-incident-20261101.md) |
| Only the summary freezes; the data model keeps cycling | `CurrentUpdateCycle` continued in every freeze with heartbeat coverage | [cross-incident table](cross-incident-20261101.md) |
| Churn raises the likelihood | 6 of 10 freezes with usable controls exceeded every control window; bursts without a freeze also occur | [cross-incident table](cross-incident-20261101.md) |
| Thread churn provokes the freeze | 9 in 1 h of load, 1 in 1 h of quiet (p ≈ 1.1%) | [stress report](stress-reproduction-20261101.md) |

## What is not established

- **One continuous chain within a single incident**, from the defective query buffer to the frozen summary. "Conflict → frozen summary" is observed; "query buffer → conflict" is not. Live tracing needs a debugger that changes timing, and is parked (A7).
- **Churn as a cause.** The cross-incident result is a temporal association on one machine and one DLL build.

## Mitigation in place

The watcher detects each freeze by the native error (visual check as fallback), restarts Task Manager, returns it to Performance > CPU and records light ETW evidence for each incident. Up to 1 November 2026 there are 150 recovery folders.

# 任务管理器 CPU 平线：总报告

[English](#en) · **中文**

以英文为准。

**已于 23:45 UTC 被[完整调查报告](investigation-report-20261101.md#zh)取代。** 本页写成后，A7 追踪已在调试器下闭合过一次"查询缓冲区 → 冲突"，N1 计数为 28 次中 28 次。

截至 2026-11-01 22:00 UTC。用一页概括整个调查，每条都链接到存放证据的文档。实时数值取自当时的 `D:\TaskmgrFreezeCaptures\status.json`。

## 结论

- **原因已定位。** `TaskManagerDataLayer.dll` 中的 `ProcessDataGenerator::QueryProcessInformation` 有两个重试缺陷：查询用尽重试时仍返回 `S_OK` 并发布缓冲区；第三次调用成功反而被判为 `E_OUTOFMEMORY`。两者都已通过直接执行该函数自身机器码的受控测试确认，覆盖 9278 和当前的 9549 文件。
- **冻结特征已在原生层面观测到。** 每次合格冻结都带有聚合冲突 `0x8007139F`（`aggregationdatamonitor.cpp:640 → :159 → Core.cpp:407`），比图表被看出变平早约 9–29 秒；冻结之外从未记录到。计数：25 次中 25 次符合。
- **可按需复现。** 线程扰动下，负载一小时内冻结 9 次，安静一小时内 1 次。
- **尚未结束。** DLL 只能由微软修复。在此之前，监测程序会自动恢复每次冻结。只有达成[路线图](roadmap.md#zh)目标 1–3，问题才算解决。

## 已确立的结论

| 结论 | 证据 | 文档 |
|---|---|---|
| 9278 和 9549 都有两个查询重试缺陷 | 原函数受控执行；9549 负对照未通过标准 1、2，通过标准 3 | [证据复核](investigation-status.md#zh)、[10-21 事件复核](flatline-incident-20261021.md#zh) |
| 9549 在 `ProcessDataSource2.cpp:821` 的错误位于 `QueryProcessInformation` 的调用方内 | 公共符号（J8） | [路线图](roadmap.md#zh) |
| 每次冻结都有 `0x8007139F` | 25 次合格冻结全部符合；冻结之外 0 次 | [跨事件表](cross-incident-20261101.md#zh) |
| 只有汇总冻结，数据模型仍在循环 | 有心跳覆盖的每次冻结中 `CurrentUpdateCycle` 都在继续 | [跨事件表](cross-incident-20261101.md#zh) |
| 进程增减提高冻结概率 | 10 次有可用对照的冻结中 6 次超过全部对照窗口；无冻结时也出现同等突发 | [跨事件表](cross-incident-20261101.md#zh) |
| 线程扰动可诱发冻结 | 负载 1 小时 9 次，安静 1 小时 1 次（p ≈ 1.1%） | [压力报告](stress-reproduction-20261101.md#zh) |

## 尚未确立的结论

- **单次事件内的完整链条**，即从有缺陷的查询缓冲区一直到汇总冻结。"冲突 → 汇总冻结"已观测到；"查询缓冲区 → 冲突"没有。现场追踪需要会改变时序的调试器，已暂缓（A7）。
- **进程增减是原因。** 跨事件结果只是时间上的关联，且只来自一台机器、一个 DLL 版本。

## 现有缓解措施

监测程序按原生错误识别每次冻结（视觉检测作后备），重启任务管理器，回到"性能 > CPU"，并为每次事件记录轻量 ETW 证据。截至 2026-11-01 共有 150 个恢复文件夹。

| 2 | 修复后的文件上 14 天且 150 有效小时，0 次 `0x8007139F`、0 次平线，并通过线程扰动检查 | 未开始；须先过目标 1 |
